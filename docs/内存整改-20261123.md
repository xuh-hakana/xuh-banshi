# 内存整改（零功能变更）

日期：2026-11-23　范围：xuhbot（src/）+ 搬屎插件（astrbot_plugin_banshi_auto）

## 原则
不发图、不压尺寸、不限张数、不截断历史、不砍重试、不改任何可见文案。产出物与改前逐字节一致，这一点有金标测试守。

## 实测数字
```
deno 跑 scripts/mem-bench.js（6 张 3MB 图 × 6 段重试）
真 node v22.21.1 下的数字（deno 的旧数字作废）：
old  rss 251MB  heap 123MB  body 24MB  154ms
new  rss 199MB  heap  75MB  body 24MB  223ms   ← body 大小完全一致=请求体等价；heap 省 48MB、RSS 省 52MB
```
结论要如实说：图片重复编码能省的是「单请求几十到几百 MB」，不是 10GB。整机 10GB 那种量级不在这一层。

## 没做的（说明原因，不是漏）
1. `setInterval` 补 clearInterval：14 个定时器都在模块顶层、进程内只启动一次，正常长跑不会叠加；只有热更新才会，收益低于改动风险。
2. 20 处 `unshift/shift` 队列：语义改动面大，收益是微秒级，先不动。
3. `data/media` 118MB、`data/media_tmp`、3 个重复备份目录：属于磁盘不属于内存，清理涉及删文件，等你点头再动。
4. llama-server：按你要求完全不碰。
5. `虚幻.app`：第三方包，只在采样器里盯。

## 采样器
```bash
cd "."
nohup bash scripts/mem-watch.sh >/dev/null 2>&1 &
tail -f data/mem-watch.log
```
每 60 秒一份快照：swap + 非 llama 进程 RSS top13 + 总量；单进程超 3G 会写 `ALERT`。

## 怎么跑（PATH 里没有 node，但 WorkBuddy 自带）
`/Applications/WorkBuddy.app/Contents/Resources/vendor/node.dat` 是 gzip 包，解开就是 Node；
WorkBuddy 的 Electron 主程序加 `ELECTRON_RUN_AS_NODE=1` 本身就是一个 Node（实测 v22.21.1）。

`scripts/node.sh` 按「`$NODE_BIN` → PATH 的 node → 已解包副本 → WorkBuddy Electron → 解包 node.dat」找运行时，找到就 exec：

```bash
bash scripts/node.sh src/bot.js                       # 起 bot
bash scripts/node.sh tests/test-img-cache.js          # 金标
bash scripts/node.sh scripts/mem-bench.js new 6 3     # 基准
# 或 npm 脚本：npm run bot:any / test:any / test:mem / bench:img
```
原有的 `npm run bot`（依赖全局 node）保持不动。

实际上这台机器有 node，只是不在 PATH：`~/.workbuddy/binaries/node/versions/22.22.2-6/bin/node`（`current` 指向它）。`scripts/node.sh` 已优先用它。

## 第二轮追加（继续排查）

| 位置 | 问题 | 修法 |
|---|---|---|
| `app/bot-runner.js` `spawnNow()` | 每次拉起 bot 都 `fs.openSync` 打开两份日志追加 fd，**父进程从不关闭** | spawn 后立刻 `closeSync` 两份 fd；重启几十次不再攒句柄 |
| `app/bot-runner.js` `nodeBin()` | 只认 `~/.workbuddy/binaries/node/versions`，找不到就退回字面量 `'node'`（PATH 里没有 → 重启后端直接失败） | 改成 `nodeCmd()`：版本目录 → WorkBuddy 内 Electron（`ELECTRON_RUN_AS_NODE=1`）→ `'node'`，并注入 env |
| `app/renderer/*` | 怀疑客户端把全部聊天/DOM 常驻 | 实测已有 `chatShowLimit: 200`/`historyLimit`/`historyChars` 上限，且 renderer 里没有任何 base64 内联图 → **不是无界增长**，不动 |
| `scripts/mem-watch.sh` | ALERT 判断拿 KB 比 MB，把每个进程都标成 ALERT | 先 `int($1/1024)` 再比，并跳过 llama-server 行 |

采样器现在在跑（`bash scripts/mem-watch.sh`，日志 `data/mem-watch.log`，60 秒一条，当前非 llama 合计 4.4GB）。

## 第三轮追加：人设缓存每轮白读一遍

| 位置 | 问题 | 修法 |
|---|---|---|
| `src/core.js` `readSoul()` | 先无条件把 `soul/F-*` 下每个 md 读完、跑一遍 `stripScenes` 解析，**再**拿 key 比缓存；命中时这些字符串全扔掉 | 拆两遍：第一遍只 `statSync` 拼 key（`readResponseBlocks` 早就是这写法，向它看齐），key 没变直接返回缓存；变了才真读 |

实测（`/tmp/soul_reads3.js`，用 monkey-patch 计数 `fs.readFileSync`）：改后连续 50 次取人设 **0 次**读人设文件，文本与首次完全一致，单次 ~0.04ms。改前是每次 5 个 md、约 48KB 全部重读 + 重新解析。

顺带把 `readSoul` 加进了 `module.exports`（自检/测试用，只是多一个导出，不影响调用方）。
